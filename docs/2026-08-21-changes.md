## 1. "상품 등록이 안 된다" 원인과 조치

### 확인된 사실 (Supabase 로그, KST)

| 시각 | 로그 |
| --- | --- |
| 12:17:41 | `POST /auth/v1/token` 200 — 관리자 로그인 성공 |
| 12:17:50 | `products` / `product_options` / `product_images` / `inventory` GET 200 — 상품 관리 페이지 렌더 성공 |
| 12:18~12:21 | `store_settings`, `analytics_events`만 기록 (고객몰 트래픽) |

**`POST /rest/v1/products`가 한 건도 없고 Storage 요청도 0건.**
→ `/api/products` 핸들러가 DB에 닿기 전에 종료됐다는 뜻입니다. 인증 실패는 배제됩니다(같은 세션으로 페이지가 렌더됐고 service role도 살아 있었음).

### 원인 (강한 추론 — Vercel 런타임 로그는 접근 권한이 없어 413을 직접 관찰하지 못함)

Vercel 서버리스 함수의 요청 본문 한도는 **4.5MB**입니다. 기존 코드는 파일당 5MB × 최대 9장(=45MB)을 허용한다고 선언했지만, 4.5MB를 넘으면 **함수 실행 전에** 플랫폼이 413을 반환합니다. 휴대폰 사진은 보통 3~5MB라 썸네일 한 장으로도 걸립니다.

그리고 오류 메시지가 화면에 전혀 뜨지 않은 이유는 별개의 버그입니다:
클라이언트가 413의 HTML 응답에 `response.json()`을 호출 → SyntaxError → 아무도 잡지 않아 조용히 종료.

### 조치

- **브라우저에서 이미지 자동 축소** (`compressImage`): 최대 변 1600px, JPEG q0.82. 5MB 사진이 보통 300~600KB가 됩니다.
- 서버/클라이언트 한도를 **총합 4MB**로 통일하고, 넘으면 장수·현재 용량을 숫자로 알려줍니다.
- `request.formData()` 실패를 413 + 안내 문구로 변환.
- HEIC 등 미지원 형식은 파일명과 실제 MIME을 찍어 안내.

## 2. 에러 로그 (요청사항)

`@closed-commerce/observability` 패키지를 새로 만들었습니다.

- 모든 서버 오류에 **requestId**(예: `K3M9X2QP`)가 붙습니다.
- Vercel 런타임 로그에는 `[cc:error] {"scope":"admin.products.create","requestId":"...","message":"...","code":"23505",...}` 형태의 한 줄 JSON이 남습니다. `[cc:error]`로 검색하면 됩니다.
- 화면에는 `오류 문구 [HTTP 400 · validation_failed · 오류번호 K3M9X2QP]` 형태로 표시됩니다.
  → 대표님이 오류번호만 알려주시면 서버 로그를 바로 찾을 수 있습니다.
- 정상 흐름의 분기점(`[cc:event]`)도 남습니다: 검증 통과, 업로드 바이트, 결제 완료 등.

바뀐 것:
- Supabase 오류의 `code`/`details`/`hint`를 보존 (예전에는 "저장하지 못했습니다"로 뭉갰음).
- Zod 검증 실패 시 **필드별 메시지**를 그대로 노출.
- 비JSON 응답(413/502/타임아웃)을 클라이언트가 잡아 상태코드와 본문 일부를 표시.
- 결과를 버리던 비동기 호출(재고 해제, 커미션 되돌리기, shipment upsert)을 전부 로깅.

## 3. 장바구니·주문 (P0)

- **`POST /api/cart/quote` 신설.** 장바구니/주문서의 상품명·단가·배송비·합계를 서버가 계산합니다. 클라이언트는 상품 id와 수량만 보관합니다. 가격 조작 여지도 사라집니다.
- **가격 계산기 통합.** `calculateCartTotals`(DEMO 기준)와 `calculateCartTotalsFromLines`(DB 기준)가 배송비 산출과 promotion 조건 검사에서 서로 달랐습니다. 이제 `calculateCartTotalsFromLines` 하나만 있습니다.
- **`KGY001` 하드코딩 9곳 제거.** 장바구니→주문서 링크가 항상 `?ref=KGY001`이었고, `order-service`가 가입 코드와 다르면 400을 내므로 **다른 코드로 가입한 회원은 결제가 100% 막히는 상태**였습니다. 이제 추천 귀속은 서버가 세션에서 읽습니다.
- **할인 배분 잔차 보정** (`allocateDiscount`): 라인별 반올림 합계가 주문 할인액과 어긋나 `order_items.commissionable_amount` 합 ≠ `orders.commissionable_amount`가 되던 문제.
- 홈 화면이 live 카탈로그를 봅니다. 비회원에게는 가격 대신 "회원 전용 가격".
- `loadProductBySlug`가 전체 카탈로그를 로드하지 않고 slug 단건을 조회합니다.

## 4. 인가 / 안전장치 (P1)

- **`apps/admin/middleware.ts` 신설.** 관리자 인가가 layout(AdminShell)에만 있었는데, App Router는 layout과 page를 병렬 실행하므로 비로그인 요청에서도 page의 service role 조회가 전부 돌았습니다.
- **`admin-data.ts`가 인증을 통과해야만 client를 얻습니다.** 예전에는 이 파일이 인증과 무관하게 service role 클라이언트를 직접 만들었습니다.
- **관리자 레이아웃에 `force-dynamic`.** 빌드 시 환경변수가 없으면 페이지가 정적 산출물이 되어 런타임 권한 확인이 통째로 건너뛰어질 수 있었습니다.
- **production fail-closed** (`resolveRuntimeMode`). 환경변수가 빠지면 예전에는 조용히 데모 모드로 넘어가 ① 주문 API가 저장 없이 "주문 접수됐어요" 200, ② 관리자 API 8개가 무인증 통과, ③ 관리자 화면이 그냥 열렸습니다. 이제 production에서는 데모 모드가 존재하지 않습니다. 데모 응답에는 `[DEMO]` 접두어가 강제됩니다.
- **`withAdmin()` / `withAdminParams()` 래퍼.** 관리자 API 8개의 동일 보일러플레이트를 걷어내고, **권한 확인이 항상 본문 파싱보다 먼저** 오도록 순서를 고정했습니다(예전에는 비인증 요청도 파일을 통째로 버퍼링).
- **주문 시 상품 visibility 검증.** `status='active'`만 보고 있어 `hidden` 상품도 id만 알면 주문됐습니다(service role은 RLS 우회).
- **가입 실패 시 고아 계정 롤백.** 귀속 저장이 실패하면 auth 사용자가 남아 영구히 주문 불가 + 재가입 불가 상태가 됐습니다.
- **결제 webhook**: 상수시간 secret 비교, 종료된 주문(취소/환불)을 `paid`로 되돌리지 못하게 상태 검증.

## 6. DB 마이그레이션 (live 적용 완료)

`supabase/migrations/20260821000600_tighten_public_read_policies.sql`

`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`는 브라우저에 노출됩니다. 기존 정책은 anon SELECT를 허용해서, 누구나 Data API로 다음을 읽을 수 있었습니다:

- `referral_codes` 전량 (초대코드 + 소유자 id) — **폐쇄몰의 핵심 자산**
- `promotion_codes` 전량, `promotion_rules`의 할인율/최소주문금액

바뀐 것:

| 대상 | 변경 |
| --- | --- |
| `referral_codes` | anon SELECT 제거 → 본인 소유 코드 또는 본인이 귀속된 코드만 |
| `promotion_codes` / `promotion_rules` | 관리자만 SELECT (고객 적용은 서버가 service role로 검증) |
| `orders_insert_self` | 삭제 — 회원이 임의 금액 주문 row를 직접 만들 수 있었음 |
| `refunds_insert_order_owner` | 삭제 — 금액 검증 없는 환불 요청 row 생성 가능했음 |
| `profiles_update_self` | 운영자/관리자도 자기 프로필 수정 가능(권한 상승은 계속 차단) |
| `product_images_visible_read` | 상품 노출 정책을 이미지에도 동일 적용 |

적용 후 Supabase security advisor: `lints: []`.

> 회원가입의 추천코드 조회를 세션(anon) 클라이언트 → service role로 옮겼기 때문에 위 정책 축소가 가능해졌습니다.

## 7. 개발 인프라

- **ESLint 도입** (`eslint.config.mjs`). 저장소에 ESLint 설정 자체가 없었고 `lint`는 `tsc --noEmit`이었습니다. 도입 직후 11건이 잡혔고 전부 수정했습니다 — `await` 뒤의 `event.currentTarget` 접근, 떠 있는 Promise, `FormData.get()`의 `String()` 변환 등.
- `@typescript-eslint/no-floating-promises`를 error로 둡니다. 재고 해제 실패가 조용히 사라지던 부류를 잡습니다.
- **커머스 테스트 3건 → 10건.** 무료배송 경계, 라인 간 배송비 최댓값, 상품 한정 프로모션, 할인 상한, 빈 장바구니, 할인 배분 잔차.
- `.gitattributes` 추가 (eol=lf) — CRLF로 항상 modified로 남던 문제.
- `.env.example`에 `ADMIN_LOGIN_EMAIL_DOMAIN`, `CC_DISABLE_DEMO` 추가. `turbo.json` globalEnv에 커미션율 3종 추가.
- `admin/next.config.ts`의 `transpilePackages`에 빠져 있던 `@closed-commerce/validation` 추가(실제로 쓰고 있었음).

## 9. 아직 남은 것 (의사결정 필요)

| 항목 | 왜 안 했는지 |
| --- | --- |
| 주문 생성 단일 트랜잭션(`create_order` plpgsql) | 실 PG 연동과 함께 하는 게 맞습니다. 지금은 8단계 개별 호출 + 보상 로직(이제 로깅은 됨) |
