# 레포 정적 점검 및 리팩토링 — 2026-09-08

범위: 고객몰·관리자 앱의 구조, 인증/인가 진입점, 상품 조회·등록·이미지 업로드, 주문·견적·결제·환불·할인 계산, 공통 패키지, 저장된 DB 마이그레이션, 검사 설정.
핵심 경로 중심의 점검이며 모든 UI/운영 DB/PG를 실결제까지 검증한 것은 아니다. 이 문서 작성 시점 이후 공식 PayDataKR v1.5 SDK와 키 역할을 확인해 결제 경로를 갱신했다.

## 운영 전 우선 과제

### 1. PG 실제 결제·환불 복구 (높음)

- 공식 매뉴얼의 v1.5 JavaScript SDK 결제창 URL과 `products` 필드, SDK의 `result`/`pay` 중첩 응답, webhook의 평면 응답을 확인했다.
- `pk_` 키는 SDK `publicKey`로 전달하고 같은 키로 `/api/echo` POST를 호출해 `0000` 응답을 확인했다. 서버는 결제 결과를 정규화한 뒤 Pay Key로 `/api/get/{transactionId}`를 재조회한다.
- 조회 검증기는 최상위 또는 `pay` 객체의 `trackId`, `transactionId`/`trxId`, `amount`가 모두 일치해야 통과한다. 실제 승인·환불 거래 자체는 아직 실행하지 않았다.
- 실패 통보가 인증되지 않았기 때문에 즉시 재고 반환을 제거했다. 취소된 결제의 재고는 기존 20분 만료 정책까지 예약될 수 있다.

### 2. 주문·결제·재고의 원자적 갱신 (높음)

- apps/web/lib/order-service.ts에서 결제 행 선점, paid 갱신, 주문 paid 갱신, 수수료, 프로모션이 별도 호출이다.
- 중간 장애 뒤에는 pending 결제 행이 재시도를 막거나 paid 결제와 pending 주문이 함께 남을 수 있다.
- 만료 작업은 orders를 잠그지만 결제 처리는 같은 DB 트랜잭션을 사용하지 않아 승인 처리와 만료가 경합할 수 있다.
- 만료 SQL은 동일 product_id의 여러 옵션 품목을 합산하지 않고 UPDATE FROM을 사용한다. 동일 상품의 복수 품목에서는 예약 전량 반환을 보장하지 못한다.
- 다음 작업: 새 마이그레이션으로 결제/주문 상태 전이 RPC와 합산 재고 반환, 알림 수신 보관 및 재처리 경로를 함께 구현한다. 중복·동시 콜백, 중간 장애, 늦은 승인·만료 경합을 로컬 DB에서 검증해야 한다.

### 3. 환불 요청 선점 및 대사 (높음)

- apps/admin/app/api/orders/[id]/refund/route.ts는 기환불 합계를 읽고 PG를 호출한 뒤 환불 이력을 저장한다.
- 동시 요청이 같은 잔액을 보고 진행할 수 있고, PG 성공 후 DB 저장 실패는 다음 요청의 판단에 반영되지 않는다. 동일 trackId를 보냈을 때 PG가 중복을 방지하는지도 확인되지 않았다.
- 다음 작업: 요청 ID가 있는 환불 시도 행을 먼저 저장·선점하고, 불명확한 결과를 재호출 전에 대사한다.
- 부분 환불 시 수수료 전액 취소는 현재 정책이다. 비례 차감으로 바꾸기 전 정책 결정이 필요하다.

### 4. 회원가의 Data API 노출 범위 (높음, 운영 확인 필요)

- 앱은 catalog-data.ts의 stripPrices로 비회원 응답에서 회원가를 제거한다.
- 저장소의 초기 RLS는 공개 상품 행과 옵션에 anon SELECT를 허용하며 테이블 권한도 부여한다. 행이 공개되면 base_price와 옵션 price도 직접 조회 가능한 구조다.
- 이번에는 운영 DB 정책과 실제 공개 상품을 조회하지 않았다. 현재 운영 노출 여부를 확인한 결론은 아니다.
- 다음 작업: 비회원용 공개 projection과 회원 가격 조회 경로를 분리하고, 가격 필드 직접 조회가 차단되는지 실제 역할별 테스트를 수행한다.

## 후속 구조 정리

- 상품 등록 API의 multipart 경로는 현재 UI(JSON 등록 + signed upload)에서 사용하지 않는다. 다른 호출자가 없는지 확인한 뒤 제거하면 4MB/20MB의 이중 규칙을 정리할 수 있다.
- order-service.ts와 cart-pricing.ts의 상품/옵션 라인 구성, store-settings.ts와 order-service.ts의 배송 설정 매핑을 공통화할 수 있다. 다만 사용자 RLS 조회와 service-role 조회의 인가 경계는 유지해야 한다.
- quoteCart, catalog-data의 비 Supabase 분기와 일부 공개 API가 unavailable을 demo처럼 취급한다. 주문 API는 이를 구분하지만 카탈로그·견적·문의 응답은 일관되게 정리할 필요가 있다.
- analytics/signup/B2B 라우트의 JSON 루트 타입·파싱 실패 처리를 통일할 수 있다.
- 조회 결과 화면은 query status로 완료 표시를 정한다. 본인 주문의 실제 DB 상태를 기준으로 표시하도록 후속 개선이 필요하다.
- 주문/수수료 상태의 타입·검증·DB 제약은 현재 여러 위치에 정의돼 있다. DB 마이그레이션 테스트를 포함한 공통 상태 정의를 검토한다.

## 검증

### 홈 이미지 최적화

- 홈 배너·카테고리·상품 카드·미니 상품의 `unoptimized`를 제거하고 Next.js WebP 변환을 활성화했다. 원본 Storage 파일은 변경하지 않는다.
- 카테고리 및 일반/컴팩트 상품 카드의 `sizes`를 실제 CSS 열 수와 중단점(580px, 1100px)에 맞췄다. 첫 배너의 우선 로딩은 유지한다.
- 운영 원본 상품 이미지 한 장은 20,295,969바이트였다. 동일 원본을 기존 운영 이미지 최적화 엔드포인트에 640px, 품질 75, Accept: image/webp로 요청하면 HTTP 200, image/webp, 30,166바이트를 반환했다(약 99.85% 감소). 이는 한 이미지의 전송량 비교이며 홈 전체 로딩 시간 개선율이 아니다.
- 전체 상품 조회와 서버 렌더링 대기, 외부 폰트는 이번 이미지 변경 범위에 포함하지 않았다. 실제 배포 후 모바일/데스크톱 화면과 로딩 지표를 추가 확인해야 한다.

### 결제 테스트 준비 상태

- 공식 SDK로 결제창 호출 및 응답 매핑을 구현했고, 고객몰·관리자 Vercel Production에 키를 등록했다. 별도 `PAYDATAKR_CHECKOUT_URL`은 사용하지 않는다.
- 코드 검사와 배포 후 제한된 테스트 주문의 승인·주문 확정·전액 환불을 실행하면 된다. 이 기록에는 실제 승인·환불 결과를 적지 않는다.
- 실운영 공개 전에는 위의 원자적 갱신/환불 복구 과제도 처리해야 한다.

### 자동 검사

- 결제 경계 회귀 테스트: 잘못된 금액, HTTP 오류, 비정상 JSON, 본문 지연, 다른 주문의 승인 재사용, metadata 위조 필드, 환불 요청 형식.
- 할인 배분 회귀 테스트: 작은 금액에서 합계·품목별 상한 보장.
- 관리자 응답 파서 테스트: 필드 오류 보존, JSON 루트 오류, HTML/413 처리. admin test를 pnpm check에 포함.
- pnpm check: 44개 작업 전체 성공. 테스트 73개 통과(결제 25, 상품/할인 15, 검증 25, 추천 3, 관리자 응답 5). 실결제/실환불 검증은 포함하지 않는다.
- 빌드에는 기존 Supabase Realtime 동적 의존성 경고가 남아 있으며 종료 코드는 0이다.
